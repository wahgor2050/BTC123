# Forward Lab 預先登記評估規則(Pre-registered Evaluation Protocol)v1

**一句講晒:呢份文件喺前向測試開始頭一日已經寫死「幾時算好、幾時算死、幾時只係繼續睇」,
之後唔准因應結果改字眼 —— 免得將來任何「候選表現好」嘅講法變成事後先劃靶。**

- 凍結日:2026-09-20(lab 啟動日,forward 數據 <1 日時寫成)
- 適用對象:`sma_1d_30d_v25_v1`(下稱 A)、`rvol2_breakout24h_v25_v1`(下稱 B)
- 呢份文件嘅 SHA-256 由每小時 run 記入 `summary.json`(`evaluation_protocol.sha256`),
  改動即刻睇得出。
- 兩個候選現時身份:**未驗證研究線索**(事後揀出、樣本薄、對成本敏感;B 仲輸埋自己嘅
  matched-control 測試、Binance 複製為負)。呢個 lab 唔係「證明咗先擺上嚟」,係收集前向證據。

## 0. 門檻嘅誠實聲明

下面所有數字門檻(−30% MDD、−20% 半年回報、8/10 次完成交易等)係**保守判斷值,唔係由
backtest 分佈推導出嚟**——原研究樣本太薄,推導唔到有意義嘅分位數。判斷值嘅作用係「劃咗
先、唔准移」,唔係聲稱佢哋有統計最優性。

## 1. 檢討時點同產出

- 檢討點:啟動後 **T+30日、T+90日、T+180日**,之後每 90 日一次。
- 每次檢討 = 跑 `python btc_lab_review.py`(確定性:只讀 append-only 檔案
  `orders_*.csv` / `opportunities_*.csv` / `equity_*.csv` + `state.json`,唔攞外部數據、
  唔用牆鐘時間做內容),將輸出 commit 入 `btc_demo/lab/reviews/`。
- 30 日未夠之前,審裁欄位一律顯示「N/A — 未夠30日」,唔准用更早嘅數字落任何判斷
  (唯一例外:第 3 節嘅 MDD 退役線隨時生效)。

## 2. 預設動作 = 繼續觀察(CONTINUE)

冇觸發第 3 或第 4 節任何一條,就乜都唔做:唔加注、唔改參數、唔宣傳、唔收檔。
「表現麻麻」唔係退役理由,「表現幾好」都唔係升級理由 —— 一切以下面凍結條件為準。

## 3. 退役(RETIRE)條件 —— 任何一條中即退

退役 = 該候選停止新開倉(`--pause`),歷史紀錄全部保留,唔刪唔改。

| # | 條件 | 適用 | 理由(判斷值) |
|---|---|---|---|
| R1 | 小時 NAV 最大回撤 ≤ **−30%**(隨時生效,唔等檢討點) | A、B | 25% vol-target 策略見 −30% 已遠超設計預期;繼續玩落去只係燒紀錄 |
| R2 | T+180日 檢討點:累計淨回報 ≤ **−20%** | A、B | 半年蝕兩成,同「線索可能有嘢」嘅先驗完全唔夾 |
| R3 | ≥T+90日 嘅檢討點:已完成交易(episode)≥ **10** 次,而累計已實現淨 PnL < 0 | B | B 係離散事件策略,10 次全加埋仲係負數 = 前向證據反對 |
| R4 | 數據紀元斷裂(Bitstamp 停服務/產品下架)而無法原樣恢復 | A、B | 換 venue = 新紀元新紀錄,舊紀錄封存,唔准縫埋一齊當連續 |

## 4. 升級(ESCALATE)條件 —— 全部同時滿足先觸發

「升級」嘅唯一意思:**通知用戶 + 排一個全新 matched-control 研究 + fresh-context 對抗式
審核**(即係入返屋企個正常研究流程)。升級**永遠唔係**加大注碼、接駁 broker、或者對外
講「已驗證」—— 前向 lab 數字本身唔准直接變成任何 claim。

| # | 條件 | 適用 |
|---|---|---|
| E1 | 檢討點 ≥ T+90日(30日檢討點冇資格觸發升級) | A、B |
| E2 | 累計淨回報 > 0 | A、B |
| E3 | 淨回報 > 同窗 date-matched 控制組回報(定義見第 5 節) | A、B |
| E4 | 已完成 episode ≥ **8** 次(B 專用;唔夠 8 次,無論數字幾靚,判「樣本未夠,繼續觀察」) | B |
| E5 | 剔走單一最好 episode 之後,淨回報符號唔准反轉(反轉 = 脆弱旗,封鎖升級) | A、B |

E4 揀 8、R3 揀 10 嘅理由:8 次係「先至勉強有得睇方向」嘅最低樣本(原 backtest 本身都係
幾十次呢個量級),10 次負數先夠膽話「反對」——退役門檻故意企高過升級樣本門檻一格,
寧願多觀察,唔好草率殺,亦唔好草率讚。

## 5. 控制組定義(凍結)

同窗 date-matched 控制:

```
control_return = (mark_end / mark_start − 1) × mean_exposure_fraction
```

- `mark_start` / `mark_end`:該候選自己 equity 檔案入面、檢討窗口首/尾快照嘅 BTC mark。
- `mean_exposure_fraction`:同一批快照嘅 `exposure_pct` 平均值 ÷ 100。
- 即係問:「同一段時間、平均攞同一份 BTC 風險,乜都唔諗淨係揸住,會拎到幾多?」
  候選連呢個都跑唔贏,就談不上有揀時機嘅價值。(規矩出處:控制組必須對齊日期,
  唔對齊會製造假 edge。)

## 6. 每次檢討必須披露(descriptive,唔係規則)

1. **成本脆弱度**:實際 paper 成交價 vs 每張單附帶嘅固定成本診斷重定價(10bp fee+2bp slip)
   嘅累計差異 —— 原研究已知對成本敏感,呢行唔准慳。
2. **運行覆蓋率**:預期小時快照數 vs 實際數(漏 run 會令 B 錯過入市機會,直接影響證據質素)。
3. **錯過/拒絕嘅機會統計**(`opportunities_*.csv` 分 decision 計數)。
4. **backtest 參考分佈對照**(第 7 節);檔案未存在就明寫 N/A。

## 7. Backtest 參考分佈(scaffold,未有數據)

檔案:`btc_demo/lab/backtest_reference.json`(**暫未生成** —— 生成需要用原研究歷史數據
重跑同長度滾動窗口,係另一件工作,要用戶開綠燈)。Schema 凍結如下,方便日後機械式填充:

純粹定位,唔係檢定;檔案未有之前,review 顯示 N/A,唔准用其他數字頂替。

## 8. 修訂規則

- 呢份文件 semantic 改動(門檻、定義、動作)= 出 v2 + 喺下面 changelog 補一行 + 新 SHA-256;
  **唔准原位改 v1 嘅規則字眼**。錯別字/排版修正可以原位改,但都要落 changelog。
- 已知殘餘風險(記錄在案,唔工程化解決):如果 lab workflow 自己死咗,每小時 commit 停止,
  GitHub 對 60 日冇活動嘅 repo 會停埋所有 schedule(包括睇門口嗰個)——後盾係 GitHub
  對 scheduled workflow 失敗嘅電郵通知。
